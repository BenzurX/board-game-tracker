# PROGRESS - Board Game Tracker

## Multiplayer Rooms (built 2026-07-23, shipped 2026-07-24 in v0.14)
`multiplayer` `cloudflare-worker` `shipped`
Cloudflare Worker + Durable Object backend with a full client (join-by-code, QR, live room bar, host/each-player scoring modes), deployed and live. Three of the original beta scope cuts have since been lifted and the host-disconnect one is much softened by the v0.22 presence grace window - read the detail file before assuming a documented limitation still holds.
→ [progress/multiplayer-rooms.md](progress/multiplayer-rooms.md)

## Group Join (built 2026-08-09, shipped in v0.19, cap raised in v0.20, renaming added in v0.22)
`multiplayer` `worker` `shipped`
One device can declare up to all 8 seats during create-room or join-room; they become full players whose scores that device enters, and since v0.22 the leader can rename them too. Deliberately locked at join time and bound to the leader's device - both were explicit calls, and the alternatives are written down in the detail file.
→ [progress/group-join.md](progress/group-join.md)

## Multiplayer Resilience and Final Round (built 2026-08-15, shipped in v0.22)
`multiplayer` `worker` `farkle` `shipped`
Presence grace window, keepalive with silent reconnect and a blocking Reconnect dialog, auto-scroll to the live round and current column, rename-anyone-you-own, in-place New Game for a live room, turn-gated score entry, and a Farkle final lap measured in turn order. The grace window and the client retry budget are deliberately paired numbers, `refreshAlarm()` is now the only thing allowed to set the Durable Object's alarm, and rounds no longer necessarily start at column one - read the detail file before touching any of the three.
→ [progress/multiplayer-resilience.md](progress/multiplayer-resilience.md)

## Tracker Chrome Auto-Hide (rebuilt 2026-08-17, shipped in v0.23)
`ui` `scrolling` `shipped`
The three tracker bars now collapse together three seconds after the last manual scroll instead of by scroll position, and only real input - wheel, drag, scrolling key - brings them back, so the app's own auto-scrolls no longer flash them at a player who never touched the screen. The input-only reveal, the momentum grace period, the `scrollTop` correction and the short-board guard each exist for a specific failure - read the detail file before adjusting any of the four.
→ [progress/tracker-chrome-autohide.md](progress/tracker-chrome-autohide.md)

## Score Entry Fixes (built and shipped 2026-08-27 in v0.24)
`custom-games` `input` `mobile` `shipped`
Two fixes to how a custom game is scored: golf direction was being read from an unscoped `.dir-btn.active` query that matched the multiplayer section's button first, so every golf game crowned the highest total, and score fields now carry a ± button because no mobile keypad offers a minus key. The switch from `type="number"` to `type="text"` is what makes the sign toggle work at all - read the detail file before putting the number input back.
→ [progress/score-entry-fixes.md](progress/score-entry-fixes.md)

## Pip Redesign (built 2026-08-27 to 2026-08-29, shipped in v0.25)
`design` `sound` `worker` `shipped`
Full visual rebuild from a Claude Design handoff: one Pip theme in two modes, eight ink-on-accent player colours, a single physical button model, the die as the player counter across all three setup flows, and a procedural Web Audio layer with a pop and a victory fanfare. The review pass found the Worker had never moved to the new palette, which had been silently rejecting every colour change players made - read the detail file before touching the token aliases, the rotation rule, or where the fanfare fires.
→ [progress/pip-redesign.md](progress/pip-redesign.md)

## Next Session

1. Test v0.25 in a real multiplayer room, on 2+ devices, after the Worker deploy. The seat-colour fix is the reason the Worker had to go out: confirm a new player joining gets a colour from the Pip eight, and that tapping a colour dot and picking a new one actually sticks for everyone rather than snapping back. Snapping back is exactly the old bug and would mean the Worker deploy did not land - check the command used was `cd worker && npx wrangler deploy -c wrangler.toml`, since without `-c` wrangler redeploys the static site and reports success.
2. Test the die on a phone, in all three flows. On setup: ± between 2 and 8, pips lighting in each player's colour, toasts at both walls, and names surviving a drop from 5 to 3 and back to 5. Hosting a room: the names typed before the room exists should be the seats inside it. Joining a room: it starts at 1, caps at the room's remaining capacity, and the three toasts should read differently for the 8-player maximum, one seat left, and N seats left. Also confirm names do not leak between games - back out of setup, pick a different game, and the fields should be empty.
3. Check the sound on a real device, the only place the autoplay policy behaves normally. The pop should fire on the first tap after a cold load (the AudioContext unlocks on that gesture, so the very first press is the one at risk of being silent), the Volume slider should scale it and mute at zero, and the victory fanfare should fire exactly once per win rather than again on every repaint, which is what the celebration gate exists to prevent. Tap the winner banner for extra confetti and confirm the fanfare does not replay with it.
4. Test the v0.24 score-entry fixes on a phone, the device the ± button exists for. In a custom game with negatives allowed: tap ± before typing (the field should show "-" and the digits land after it), tap it again to go back positive, and tap it on a cell you are correcting inline - that one is the case that used to close the editor on the tap, since it commits on blur. Confirm a field left holding only "-" is treated as blank rather than as 0, and that the button is absent in games where negatives are not legal (Farkle, Yahtzee). Separately, run a custom game set to "Lowest wins (golf)" past its target and confirm the lowest total is crowned - the crosser should usually lose. Worth one Farkle round too: its desktop spinner no longer steps by 50, so check a typed 137 still lands as 150.
5. Re-test the Farkle final round after the closed-seat fix. The reported bug (a device on seats 1-3 still being offered the crosser's row in the extra round) was fixed and confirmed on device; what has not been re-tested is the rest of the lap. Test with 4+ players, deliberately crossing the target from a middle seat. Whoever played after the crosser should finish that round, whoever played before them should get their turn in the next one, the FINAL ROUND toast should name the crosser, and the game should end right after - not a round early, not a round late. Run it twice: once with the default order, and once with the host declaring a first player other than player 1, since turn order then rotates and a crosser who led the round off must end the game with that round and no extra turns at all. Check solo scoring and both multiplayer modes.
6. Test the v0.22 presence and reconnect work on 2+ real devices - none of it has run in the real app. Worth covering: a refresh taken on your own turn (name must not strike out, turn must not skip, no ✗ in the round), a phone locked for a minute or two, a backgrounded tab left long enough for the OS to throttle it, and airplane mode held past the four retries so the blocking Reconnect dialog appears and the reload rejoins the same seat.
7. Test turn-gated score entry in an "Each Player Enters Score" room where one device holds several seats. With the run starting on that device's last seat it should be asked for that one score only; with the run starting on its first seat it should be asked for the whole contiguous block; and when the turn sits on another device's seat the Enter Score button should read as locked and say whose turn it is. Check it again after the host declares a first player mid-setup, and confirm host-scoring rooms still enter the whole round in one pass.
8. Test the v0.23 idle-timer tracker bars on a phone, where the vertical space they cost is the whole point. All three should go together about three seconds after you stop scrolling, and a drag, a wheel or an arrow key should bring all three back at once. The cases worth trying to break: a round landing on another device mid-game must not reveal them (that auto-scroll is the reason the reveal moved off the `scroll` event); a flick with momentum must not drop them mid-glide; the board must not slide under your finger when they go, which is the `scrollTop` correction and the thing most likely to be visibly wrong first; reaching slowly for the gear or Enter Score must not have the bar collapse out from under you; and a board too short to scroll must keep all three pinned forever, since nothing could bring them back. Also check a short board that grows past the threshold as rounds land - the countdown has to start itself there, via the ResizeObserver, with no scroll event to trigger it. The floating ⊕ button goes with it: it should appear only while the footer bar is gone, stay clear of the totals row and the round being played at any font size, and in a multiplayer room read as locked and toast whose turn it is exactly as the bar does.
9. Test the board animations on a real device, in a multiplayer room where a second device is entering scores. Each should fire exactly once for its own cause: a total counting up when it changes, the new round sliding in, a changed cell tinting once, the turn highlight landing on the column that just took the turn. The cases worth trying to break are the ones where nothing should animate - resuming a saved game, joining or rejoining a room, and a host reset should all paint silently rather than flashing every cell, and rapid score entry should not leave a total stuck mid-count. Watch the rightmost column specifically: its score is the one that completes the round, so it takes an extra render mid-count and was the case where the count-up used to snap to the final number instead of running. Check it again with OS reduced-motion on, where all of it including the winner banner's pop should be inert.
10. Test New Game inside a live room: host plus at least one guest should restart in place on the same code with the roster intact and the host on turn one, and guests should see the toast. Confirm the Back button still closes the room, and that a solo host or a guest still gets the old leave behaviour.
11. Test the widened rename permissions: a guest renaming their own seat and a group member they added, the host renaming anyone, and a guest failing to rename someone else's seat (the Worker's check is the one that matters, not the client's).
12. Test the v0.21 your-turn card on 2+ real devices - it shipped without ever running in the real app. Worth covering: that it fires exactly once per turn handoff (not twice, once from `round-update` and once from `turn-update`), that it stays silent on rejoin, that a Farkle final round still announces turn by turn while the handoff that crowns the winner does not, and that the shimmer reads correctly in light mode, where the highlight sits close to the accent colour. Auto-scroll should now be putting the announced column on screen, so check the two together.
13. Test group join on 2+ real devices - it is deployed but has not been exercised end to end. Worth covering: a 3-person group joining mid-game, the host removing one member vs removing the group leader, and a refresh on the leader's device restoring the whole group.
14. Verify the join die against a nearly-full room (try to take 2 when only 1 seat is left) - the seat count comes from `/room/:code/exists` and can go stale, so the server rejection path is the one that actually matters, not the client-side cap the die enforces.
15. Sanity-check the v0.20 cap raise: a host claiming all 8 seats on one device leaves nobody to join, and the Enter Score modal then renders 8 rows. Confirm the modal stays usable at that size on a phone and that the room still behaves sensibly with a single connected socket.
16. Decide the win-logic philosophy (deferred 2026-07-09): should the tracker enforce game rules or just record scores? On tied winning totals the earlier-seated player silently wins (`indexOf` picks the first match) - decide tie handling (shared win banner? sudden-death round?).

## Backlog
- Solo play still lets the crosser score again in the final round - `finalLapClosedSeats()` returns empty for solo on purpose, because a solo round is entered whole and excluding a seat would leave a null cell that Farkle renders as a mark. Needs the cell rendering decided before the exclusion can be applied
- The Worker has no final-round concept: `canScoreFor` will accept a score for a seat the final lap has closed, and `findNextUnsubmittedPlayerId` still cycles the turn onto one. Enforcement is client-side only, so a stale client could push a score the rules do not allow
- More games (round-by-round and category-based scoring)
- Payment/entitlement gating for multiplayer, deferred to before v1.0
- Host reassignment when the host disconnects mid-game (currently the room just loses host-only controls until they return)
